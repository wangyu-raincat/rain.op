# JwtQA

JWT 安全离线问答与令牌结构自查：用 10 张知识卡片讲清 JWT 常见攻击手法与防御，并能直接解析一个 JWT 的 header / payload，指出结构上的可疑点。纯 Python 标准库，离线可运行，不联网、不调用外部 API。

## 它能做什么

| 功能 | 说明 |
| --- | --- |
| `--ask` | 向本地知识库提问，BM25 式词项检索返回相关卡片 |
| `--inspect` | 只解析 JWT 的 header / payload 结构，打 0–100 风险分并给出处置建议 |
| `--demo` | 演示：3 个示例令牌自查 + 3 个典型问答 |

## 知识卡片（10 张）

| 卡片 | 主题 |
| --- | --- |
| jwt-01 | JWT 结构：三段式与 payload 可读 |
| jwt-02 | alg=none：无签名伪造 |
| jwt-03 | 密钥混淆：RS256 被当成 HS256 验 |
| jwt-04 | 弱密钥：HS256 离线爆破 |
| jwt-05 | kid 注入：目录遍历与 SQL 注入 |
| jwt-06 | jku/x5u 劫持：自带密钥地址不可信 |
| jwt-07 | exp 与吊销：过期校验与有效期 |
| jwt-08 | 敏感信息：不要把密码放进 JWT |
| jwt-09 | 只解码不验签：最常见的实现错误 |
| jwt-10 | JWT 防御清单：十条自查项 |

知识内容为 JWT 通用安全知识（对应 RFC 7519 与 OWASP JWT 安全清单的常见条目），不针对某个具体厂商实现；处置前请结合自家服务端的验签逻辑复核。

## 怎么跑

```bash
# 离线演示
python jwtqa.py --demo

# 问答
python jwtqa.py --ask "alg=none 有什么危害？"
python jwtqa.py --ask "RS256 变成 HS256 是怎么攻击的？"
python jwtqa.py --ask "JWT 里能放密码吗？"

# 自查一个令牌（只解析结构，不校验签名）
python jwtqa.py --inspect eyJhbGciOiJub25lIi... 
```

## 自查规则

| 检查 | 风险 |
| --- | --- |
| alg=none | 高危：可能被无签名伪造 |
| header 缺少 alg | 高危：解析行为不可预期 |
| kid 含 `../`、`\` 或 SQL 特征字符 | 高危：目录遍历 / 注入 |
| jku / x5u 存在 | 高危：密钥地址可能被劫持 |
| payload 含密码、密钥类敏感字段 | 高危：payload 人人可读 |
| 缺少 exp / exp 已过期 | 中危：泄露后可长期使用 |
| exp 有效期超过 7 天 | 低危：泄露窗口过大 |
| alg=HS256 | 提示：安全性取决于密钥强度 |
| payload 声明管理员身份 | 提示：关键操作仍需服务端授权检查 |

## 示例输出

```text
=== JwtQA 演示：令牌结构自查 ===

令牌自查：alg=none 的伪造令牌：风险分 100（高危）
  header : {"alg": "none", "typ": "JWT"}
  payload: {"sub": "attacker", "role": "admin", "iat": 1700000000}
  [高危] alg=none：令牌声明不使用签名，若服务端接受无签名令牌，攻击者可任意伪造身份。请确认服务端拒绝 alg=none。
  [中危] payload 缺少 exp：令牌永不过期，一旦泄露可长期使用，建议设置较短有效期并配合刷新机制。
  [提示] payload 声明了管理员身份：请确认服务端以签名校验后的声明为准，且关键操作另有服务端授权检查，不要只信令牌里的角色。

令牌自查：kid 带路径穿越的令牌：风险分 100（高危）
  header : {"alg": "HS256", "kid": "../../etc/passwd"}
  payload: {"sub": "user1", "exp": 9999999999}
  [提示] alg=HS256：安全性取决于密钥强度与保密；弱口令密钥可被离线爆破，且密钥一旦泄露，所有令牌都可伪造。
  [高危] kid 含路径字符（../../etc/passwd）：可能存在 kid 目录遍历，攻击者借此指定任意文件作为 HMAC 密钥。
  [低危] exp 有效期超过 7 天：有效期越长，泄露后的窗口越大，建议按业务需要缩短。

令牌自查：相对规范的令牌：风险分 15（低危）
  header : {"alg": "RS256", "typ": "JWT"}
  payload: {"sub": "user2", "role": "user", "exp": 1999999999, "iat": 1700000000, "iss": "demo-app"}
  [提示] alg=RS256：非对称签名，公钥可公开；但要警惕密钥混淆攻击——服务端绝不能把 RSA 公钥当作 HMAC 密钥去验 HS256。
  [低危] exp 有效期超过 7 天：有效期越长，泄露后的窗口越大，建议按业务需要缩短。

=== JwtQA 演示：典型问答 ===

问：alg=none 有什么危害？
答：JWT 防御清单：1）服务端始终验签，alg 用白名单；2）拒绝 alg=none；3）HS256 用高熵密钥并定期轮换，RS256 密钥与算法严格配对；4）kid 只作固定映射键；5）不信任 jku/x5u；6）强制 exp 且有效期尽量短；7）payload 只放最小声明、不放敏感信息；8）令牌只走 HTTPS，存储注意 XSS 窃取风险；9）关键操作另做服务端授权检查，不只信令牌里的角色。

问：RS256 变成 HS256 是怎么攻击的？
答：密钥混淆攻击：服务端用 RS256 非对称算法签发，但验签时错误地把公开的 RSA 公钥当作 HS256 的 HMAC 对称密钥。攻击者用公开的公钥作 HMAC 密钥自己签名，服务端就会验过。防御：验签算法与密钥类型严格配对，禁止服务端按令牌 header 自选算法。

问：JWT 里能放密码吗？
答：JWT 里能放密码吗？不能。payload 只是 base64 编码，任何人解码即见明文。密码、身份证号、银行卡、密钥等敏感信息绝不能放进令牌；只放完成授权所需的最小声明（如用户 ID、角色、过期时间），且令牌只走 HTTPS 传输。
```

## 边界

`--inspect` 是结构自查，不是安全审计：它看不到服务端的密钥与校验逻辑，只能指出令牌本身可疑的地方，不能判定一次请求是否真的能绕过校验；“未见风险”也不等于安全，仍需确认服务端正确验签、校验 exp/aud/iss。示例令牌均为演示用伪造数据，不对应真实系统。
